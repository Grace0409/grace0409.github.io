## 서론

### 선정 이유

1. 제 연구 질문과 겹칩니다. 12월에 발표하는 [ZT-SVF](/posts/zt-svf-mobisec2026/)는 "공격자가 방어 규칙을 알아내고 탐지에 안 걸리는 쪽으로만 움직이면 어떻게 막을까"에서 출발했습니다. 이 발표의 공격자도 그렇게 움직입니다. 보안 제품이 수상하게 볼 행동은 피하고, 윈도우가 가장 믿는 Windows Update에 올라탑니다. 시뮬레이션으로만 다뤄 본 위협 모델이 실제 운영체제에서는 어떤 모습인지 보고 싶었습니다.
2. 요즘 만드는 도구와 닿아 있습니다. AI 에이전트 작업 기록의 변조 여부를 검증하는 [증거 게이트웨이](/posts/eil-evidence-gateway/)를 만들면서 "검증은 했는데 그 검증은 믿어도 되나"를 계속 고민했습니다. 이 발표는 서명과 무결성 검사를 갖춘 시스템이 어디서 새는지 하나씩 짚습니다.
3. 12월 MobiSec 2026에서 첫 국제학회 구두발표가 있습니다. 지금까지는 포스터 발표만 해 봤습니다. 공격 연구를 영어로 어떻게 풀어 가는지, 잘 짜인 발표 하나를 뜯어보고 싶었습니다. DEF CON과 Black Hat에 같은 내용으로 모두 선정된 발표라 교재로 삼기에 좋았습니다.

## 본론

### 1. 출발점이 된 BlackLotus

연구는 2023년에 나온 BlackLotus UEFI 부트킷에서 시작합니다. Secure Boot는 부팅 체인의 각 단계가 다음 단계의 서명을 확인하는 구조입니다. 서명이 없으면 로드되지 않으니 부트 매니저를 바꿔치기하던 예전 수법은 막혔습니다.

BlackLotus는 새 제로데이를 쓰지 않았습니다. 서명은 정상인데 취약한 옛 부트 매니저로 되돌린 다음, 이미 알려진 취약점을 다시 이용했습니다. 서명 검증은 마이크로소프트가 만든 파일인지만 확인했고, 지금도 안전한 버전인지는 묻지 않았습니다. 마이크로소프트는 취약한 부트 매니저를 폐기 목록에 넣어 대응했습니다.

발표자는 여기서 질문을 던집니다. Secure Boot 말고 다른 구성 요소도 같은 문제를 안고 있지 않을까? 서드파티 드라이버를 들고 와 커널을 공격하는 BYOVD(Bring Your Own Vulnerable Driver)를 본떠, 이번에는 마이크로소프트 자체 구성 요소를 되돌리는 "Bring Your Own Vulnerable Windows"를 목표로 잡았습니다.

### 2. 다운그레이드 성공 조건 4가지

본격적인 내용에 앞서 성공 기준부터 정의합니다.

| 조건 | 의미 |
| --- | --- |
| Fully Undetectable | 가장 정상적인 방법으로 되돌려서 보안 제품이 막지 못함 |
| Invisible | 되돌린 뒤에도 시스템은 최신 상태로 보임 |
| Persistent | 이후 업데이트가 되돌린 상태를 덮어쓰지 못함 |
| Irreversible | 검사, 복구 도구가 손상을 찾지도 고치지도 못함 |

발표 전체가 이 표를 뼈대로 움직입니다. 기법이 하나 나올 때마다 슬라이드 제목이 네 조건 중 하나로 돌아옵니다.

### 3. Windows Update의 설계 결함

윈도우 시스템 파일은 TrustedInstaller라는 별도 권한만 고칠 수 있고, 관리자도 직접 덮어쓰지 못합니다. 관리자에서 이 권한으로 올라가는 방법은 공개돼 있지만 보안 제품이 그 행동을 악성으로 잡습니다. 첫 번째 조건에 걸리는 셈입니다.

그래서 발표자는 다운그레이드를 할 거라고 가장 예상하기 어려운 구성 요소를 고릅니다. Windows Update 자신입니다. 파일을 바꾸는 게 원래 하는 일이니 이 경로로 되돌리면 이상해 보일 이유가 없습니다.

업데이트 과정을 거칠게 나누면 세 단계입니다. 업데이트 파일을 받아 서명과 해시로 검증하고, 재부팅 때 무엇을 바꿀지 적은 작업 목록을 만들고, 재부팅하면서 목록대로 파일을 교체합니다.

발표자는 업데이트 파일부터 살폈습니다. 서명이 없는 파일이 섞여 있어 빈틈처럼 보였지만, 최종 결과물의 해시가 서명된 파일 안에 들어 있어서 막혔습니다. 이 실패를 발표에 그대로 넣은 점이 좋았습니다. 가장 의심스러운 곳이 왜 안 되는지 먼저 보여 주니, 뒤에 나오는 구멍이 운이 아닌 분석 결과로 들렸습니다.

구멍은 작업 목록 쪽에 있었습니다. 목록 파일은 보호받았지만, 시스템이 어느 목록을 처리할지 기억해 두는 설정값은 보호받지 못했습니다. 관리자라면 이 값을 바꿔 자기가 만든 목록을 가리키게 할 수 있었습니다.

문제는 검증 시점이었습니다. 무결성 검사는 업데이트 파일을 받을 때 끝나고, 작업 목록은 그 뒤에 만들어지기 때문에 이미 검증된 것으로 취급됩니다. 내용물은 지켰는데 내용물의 위치를 가리키는 값은 지키지 않았습니다. 그 결과 Windows Update가 공격자 대신 파일을 옛 버전으로 되돌려 주고, 수상한 권한 상승은 한 번도 일어나지 않습니다.

### 4. 검사 도구의 무결성 문제

| 조건 | 성립 이유 |
| --- | --- |
| Invisible | 무언가를 지운 게 아니고 "업데이트"를 했으니 시스템은 최신으로 보임 |
| Persistent | 작업 목록을 처리하는 도구가 서명 검증을 받지 않아, 이후 업데이트가 아무것도 바꾸지 못하게 만들 수 있었음 |
| Irreversible | 시스템 무결성 검사, 복구 도구도 서명 검증을 받지 않아 손상을 못 찾게 만들 수 있었음 |

표의 아래 두 줄이 가장 오래 남았습니다. 업데이트를 처리하는 도구도, 무결성을 검사하는 도구도 검증 대상이 아니었습니다. 검사기를 바꿀 수 있다면 검사 결과는 늘 "이상 없음"으로 나옵니다.

첫 데모(11:40 무렵)가 이 흐름을 보여 줍니다. 업데이트 화면에서 "최신 상태"를 확인하고, 패치된 커널 드라이버를 노린 공격이 실패하는 장면이 먼저 나옵니다. 드라이버를 되돌리고 재부팅하면 같은 공격이 성공합니다. 업데이트 화면은 그대로 "최신 상태"입니다.

### 5. VBS의 fail-open 부팅

첫 데모는 관리자에서 커널로 올라간 경우입니다. 마이크로소프트 기준으로 이건 보안 경계를 넘은 게 아니고, 발표자도 이 점을 먼저 인정합니다. 대신 많은 사용자가 관리자 계정을 쓰고 윈도우 기본값도 관리자라서 위협이 사라지지 않는다고 덧붙입니다.

이 문제에 대한 마이크로소프트의 답이 VBS(Virtualization-Based Security)입니다. 커널이 이미 뚫렸다고 가정하고, 하이퍼바이저로 커널보다 안쪽에 격리된 공간을 만듭니다. 일반 운영체제가 도는 VTL 0과 보안 기능이 도는 VTL 1로 나누고, 자격 증명을 지키는 Credential Guard나 코드 무결성을 강제하는 HVCI를 VTL 1에 둡니다. VTL 0에서 VTL 1로, 커널에서 하이퍼바이저로 넘어가는 것은 명확한 보안 경계입니다.

관리자가 설정만 바꿔 VBS를 꺼 버리면 소용이 없으니 "UEFI lock"이라는 보호 장치도 있습니다. 설정을 UEFI 변수에 잠가 두고, 풀려면 부팅 중에 사용자가 직접 승인해야 합니다. 원격 공격자는 끌 수 없다는 전제입니다.

발표자는 VBS 핵심 파일이 망가져 있으면 어떻게 되는지 확인했습니다. 복구 모드로 빠질 거라고 예상했는데 실제로는 부트 로더가 검증에 실패한 뒤 VBS 없이 평소처럼 부팅했습니다. 보호 기능이 실패했을 때 닫히지 않고 열린 쪽으로 넘어간 겁니다(fail-open). 공격자는 VBS를 뚫을 필요 없이 실패하게 만들기만 하면 됐습니다.

복잡한 공격 체인 한가운데에 단순한 설계 판단 하나가 끼어 있었다는 게 인상적이었습니다. 두 번째 데모(19:00 무렵)는 Credential Guard, LSASS 보호, Defender가 모두 켜진 PC에서 재부팅 한 번 만에 셋 다 무력화되는 장면입니다. 업데이트 화면은 이번에도 "최신 상태"입니다.

### 6. 보안 경계별 다운그레이드 결과

발표 후반은 진짜 보안 경계를 다운그레이드로 넘을 수 있는지 차례로 확인합니다.

| 대상 | 되살린 취약점 | 넘은 경계 |
| --- | --- | --- |
| Credential Guard | CVE-2022-34709 | VTL 0 사용자 모드 → VTL 1 사용자 모드 |
| Secure Kernel | CVE-2021-27090 | VTL 0 사용자 모드 → VTL 1 커널 |
| Hyper-V 하이퍼바이저 | 2년 전 버전으로 되돌림 | VTL 0 사용자 모드 → 하이퍼바이저 |

세 대상 모두 버전 확인이나 폐기 목록 같은 다운그레이드 방지 장치가 없었습니다. 발표자는 당장 익스플로잇으로 이어지지 않더라도 방지 장치가 없다는 사실 자체를 취약점으로 봤습니다. 앞으로 패치될 취약점이 전부 되살릴 수 있는 무기가 되기 때문입니다. 이 판단 기준이 기억에 남습니다.

세 번째 데모(28:00 무렵)에서는 하이퍼바이저가 2년 전 버전으로 돌아갔는데도 VBS와 Credential Guard가 평소처럼 돌아갑니다.

### 7. 권한 없는 사용자의 경로

관리자 권한이 필요 없는 경로도 하나 나옵니다. 업데이트 후 복원용으로 남겨 두는 옛 운영체제 폴더에 일반 사용자가 전체 권한을 갖고 있었습니다. 폴더 안 파일은 원래 권한을 물려받아 안전했지만 폴더 자체는 아니었습니다. 관리자가 나중에 복원을 실행하면 공격자가 준비한 운영체제가 쓰일 수 있었습니다. 내용물은 지키고 그릇은 지키지 않은 패턴이 여기서도 반복됩니다.

### 8. 공개 이후 대응

발표자는 2024년 2월 마이크로소프트에 제보했고 CVE-2024-21302, CVE-2024-38202가 발급됐습니다. 대응은 한 번에 끝나지 않았습니다. 8월 발표 시점에는 CVE-2024-38202 패치가 없었고 10월에야 배포됐습니다. CVE-2024-21302는 마이크로소프트가 서명한 폐기 정책을 따로 적용하는 방식이어서, 관리자가 직접 설정해야 하는 완화책에 가깝습니다.

같은 해 10월에는 후속 연구가 공개됐습니다. 관리자에서 커널은 보안 경계가 아니라는 이유로 막지 않은 경로를 이용해, 이미 패치된 드라이버 서명 강제 우회를 최신 Windows 11에서 되살렸습니다. "경계가 아니니 고치지 않는다"는 판단이 어떤 여지를 남기는지 보여 준 사례입니다. 운영 중인 시스템이 있다면 MSRC의 두 CVE 항목을 직접 확인해 보시길 권합니다.

## 결론

### 장점과 아쉬운 점

장점

- 성공 조건을 먼저 세우고 하나씩 채워 가는 구성이라 35분 동안 흐름을 놓치지 않습니다.
- 데모 세 개가 "최신 상태 확인, 공격, 다시 최신 상태 확인"이라는 같은 틀로 반복돼 메시지가 분명하게 남습니다.
- 어디까지가 보안 경계인지 마이크로소프트 기준으로 짚어 주니, 결과의 무게를 스스로 가늠할 수 있습니다.

아쉬운 점

1. 대부분의 시나리오가 관리자 권한을 전제로 합니다. 발표자가 이유를 설명하긴 하지만, 위협 모델을 처음 접하는 사람에게는 와닿기 어려울 수 있습니다.
2. 하이퍼바이저 부분은 특정 취약점을 직접 보여 주지 않습니다. 2년 전 버전이면 고쳐진 취약점이 하나쯤 있을 거라는 논리여서 앞의 두 사례보다 근거가 약해 보였습니다.
3. 방어 쪽 이야기가 적습니다. 무엇을 모니터링하고 폐기 정책을 언제 적용할지는 발표 밖에서 찾아야 했습니다.
4. VTL, Secure Kernel 같은 배경 설명이 빠르게 지나갑니다. 윈도우 내부 구조가 낯설다면 슬라이드를 옆에 띄워 두고 보는 편이 낫습니다.

### 내 연구와의 공통점

1. 정찰하는 공격자는 정상 경로를 고릅니다. ZT-SVF의 공격자는 재인증 정책을 관찰해 걸리지 않는 위험 상태에 머뭅니다. Windows Downdate의 첫 번째 조건도 같은 생각에서 나왔습니다. 보안 제품이 무엇을 악성으로 보는지 알고, 그 규칙에 걸리지 않는 정상 경로를 골랐습니다. 탐지 규칙이 고정돼 있고 공격자가 그 규칙을 알면 결국 규칙 바깥으로 돌아갑니다. 제 논문이 "규칙을 들켜도 이득이 없게" 만드는 방향을 택한 이유를 운영체제 사례로 다시 확인했습니다.
2. 검증 대상을 가리키는 값도 지켜야 합니다. 증거 게이트웨이를 만들면서 해시 체인만으로는 전체 재계산을 막지 못한다는 걸 알고, 마지막 해시를 로그와 분리된 곳에 앵커로 남겼습니다. Windows Update는 작업 목록 파일을 지켰지만 어느 목록을 읽을지는 지키지 않았습니다. 제 게이트웨이에서도 앵커 저장 위치나 검증 키 경로를 정하는 설정이 에이전트 손에 닿는 곳에 있다면, 앵커를 분리한 의미가 사라집니다.
3. 설계도 공격 표면입니다. VBS의 fail-open도, 하위 권한 영역이 상위 권한 영역의 파일을 업데이트할 수 있었던 것도 코드 실수가 아닌 설계 판단이었습니다. 처음 제안한 CPP-DMA의 약점 역시 예측값에 기대는 구조 자체에 있었습니다. 제가 만든 걸 제가 공격해 본 경험 덕분에 이 발표가 더 잘 읽혔습니다.

### 내 연구와의 차별점

| 구분 | Windows Downdate | 내 연구 (ZT-SVF, 증거 게이트웨이) |
| --- | --- | --- |
| 목적 | 실제 운영체제의 설계 결함을 찾아 공격 가능성을 증명 | 공격자가 규칙을 알아도 버티는 방어를 설계 |
| 증명 방식 | 실제 시스템에서의 데모 | 균형 확률의 폐형식 유도와 시뮬레이션, 결함 주입 테스트 |
| 공격자 출발점 | 관리자 권한을 가진 내부자 | 세션을 관찰하며 정책을 추정하는 공격자 |
| 대응 방향 | 서명 검증, 폐기 목록 같은 규칙 보강 | 규칙이 공개돼도 기대이득이 0 이하가 되도록 확률 설계 |

가장 큰 차이는 증명의 무게입니다. 이 발표는 화면에서 공격이 실제로 성공하는 걸 보여 줍니다. 제 연구는 수식과 시뮬레이션으로 보장을 말합니다. 청중을 설득하는 방식이 다를 수밖에 없어서, 제 발표에서는 "수식이 실제로 무엇을 막는지"를 장면처럼 보여 줄 방법을 고민해야겠다고 느꼈습니다.

새로 생긴 질문도 있습니다. ZT-SVF는 위험 상태 `s`가 정해지면 재인증 확률 `p*(s)`를 계산합니다. 그런데 ZTNA는 위험도를 매길 때 흔히 기기 상태, 예를 들어 OS 패치 수준을 신호로 씁니다. Windows Downdate는 바로 그 신호를 거짓으로 만듭니다. 공격자가 이득 함수 대신 상태 관측을 속이면 균형 확률이 얼마나 흔들릴지, MobiSec 질의응답 대비 겸 다음 연구 주제 후보로 적어 둡니다.

### 내가 가져갈 것

MobiSec 2026에서 ZT-SVF를 영어로 발표할 때 이 발표의 구성을 빌려 오려고 합니다.

1. 성공 조건을 먼저 보여 줍니다. "정찰해도 기대이득 0 이하, 학습 단계 없음, 정상 사용자 부담 최소"를 앞에서 요구 조건으로 세우고, 결과 슬라이드마다 어떤 조건을 확인하는지 표시하겠습니다.
2. 핵심 문장을 처음과 끝에 둡니다. 이 발표는 "fully patched라는 말이 의미를 잃는다"로 시작하고 같은 말로 끝납니다. 제 문장은 "Even if the attacker learns the policy, evasion does not pay." 정도로 다듬어 볼 생각입니다.
3. 비교는 같은 틀로 합니다. 고정 임계값, DR-TBAC, ZT-SVF 결과를 같은 축 그래프에 같은 순서로 놓아, 청중이 그래프 읽는 법을 한 번만 익히면 되게 하겠습니다.
4. 막힌 길도 보여 줍니다. 강화학습 방식이 0과 1로 쏠리면서 사각지대가 생기는 장면을 숨기지 않겠습니다. 제안 방법이 왜 필요한지가 그 장면에서 나옵니다.
5. 예상 반론은 먼저 꺼냅니다. 발표자가 "관리자에서 커널은 경계가 아니다"를 스스로 먼저 말했듯, 저도 "공격자의 이득과 손실을 방어자가 어떻게 아느냐"를 먼저 묻고 추정이 틀려도 보장이 선형으로만 약해진다는 분석을 보여 주겠습니다.
6. 중요한 문장은 두 번 말합니다. VBS 우회를 설명할 때 발표자는 "I repeat"라고 한 뒤 같은 문장을 다시 말했습니다. 모국어가 아닌 언어로 발표할 때 쓰기 좋은 방법입니다. 슬라이드 글자는 줄이고 꼭 남길 문장은 말로 두 번 하겠습니다.
7. 열린 질문으로 마무리합니다. 마지막 슬라이드에 "상태 관측 자체를 속이면?"을 다음 연구 질문으로 남겨, 질의응답이 이어질 거리를 만들어 두겠습니다.

### 총평

"패치를 다 했으니 안전하다"는 말이 무엇에 기대고 있는지 다시 생각해 봤습니다. 업데이트 기록과 버전 번호는 결국 시스템이 스스로 보고하는 값입니다. 그 보고를 만드는 경로가 오염되면 숫자는 남아도 의미는 사라집니다. 제로트러스트가 기기의 자기 보고를 그대로 믿지 말라고 하는 이유를 구체적인 장면으로 이해하게 됐습니다.

발표자의 마지막 교훈도 메모해 둡니다. BlackLotus는 이미 1년 전에 공개된 사례였고, 그 원리를 한 단계 넓혔더니 가상화 스택 전체가 영향을 받았습니다. 공격 사례를 보면 그 취약점이 고쳐졌는지에서 멈추지 말고, 같은 원리가 또 어디에 통할지 물어봐야 합니다. 연구 주제를 찾을 때도 써먹을 수 있는 습관이라 오래 기억해 두려고 합니다 :)

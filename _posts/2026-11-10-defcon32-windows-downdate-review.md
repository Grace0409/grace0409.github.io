## 이 발표를 고른 이유

세 가지 이유로 골랐습니다.

첫째, 제 연구 질문과 겹칩니다. 12월에 발표하는 [ZT-SVF](/posts/zt-svf-mobisec2026/)는 "공격자가 방어 규칙을 다 알아내고, 탐지에 안 걸리는 쪽으로만 움직이면 어떻게 막을까"에서 출발했습니다. 이 발표의 공격자도 똑같이 움직입니다. 보안 제품이 수상하게 볼 행동은 전부 피하고, 윈도우가 가장 믿는 경로인 Windows Update에 올라탑니다. 제가 시뮬레이션으로 다룬 위협 모델이 실제 운영체제에서 어떤 모습인지 볼 수 있겠다고 생각했습니다.

둘째, 요즘 만들고 있는 도구와도 닿아 있습니다. AI 에이전트의 작업 기록이 바뀌지 않았음을 증명하는 [증거 게이트웨이](/posts/eil-evidence-gateway/)를 만들면서 "검증은 했는데, 그 검증을 믿어도 되나"라는 질문을 계속 붙잡고 있었습니다. 이 발표는 서명과 무결성 검사를 꼼꼼히 갖춘 시스템이 어디서 새는지를 하나씩 보여 줍니다.

셋째, 12월 MobiSec 2026에서 첫 국제학회 구두발표를 합니다. 지금까지는 포스터로만 서 봤습니다. 공격 연구를 영어로 어떻게 풀어 가는지, 잘 짜인 발표를 하나 뜯어보고 싶었습니다. 같은 내용으로 DEF CON과 Black Hat에 모두 선정된 발표라 교재로 삼기 좋았습니다.

## 기. 배경과 문제 정의

### 1-1. 출발점, BlackLotus

연구는 2023년에 나온 BlackLotus UEFI 부트킷에서 시작합니다. Secure Boot는 부팅 체인의 각 단계가 다음 단계의 서명을 검증하는 구조입니다. 서명이 없으면 로드되지 않으니, 부트 매니저를 몰래 바꿔치기하던 예전 방식은 막혔습니다.

BlackLotus는 새 제로데이를 쓰지 않았습니다. 서명은 정상이지만 취약한 옛 부트 매니저로 되돌린 뒤, 이미 알려진 취약점을 다시 이용했습니다. 서명 검증은 "마이크로소프트가 만든 파일인가"만 확인할 뿐 "지금도 안전한 버전인가"는 묻지 않았던 겁니다. 마이크로소프트는 취약한 부트 매니저를 폐기 목록에 넣는 것으로 대응했습니다.

### 1-2. 연구 질문

발표자는 여기서 질문을 하나 던집니다. Secure Boot 말고 다른 구성 요소도 같은 문제를 갖고 있지 않을까?

서드파티 드라이버를 가져와 커널을 공격하는 BYOVD(Bring Your Own Vulnerable Driver)는 잘 알려진 기법입니다. 발표자는 대상을 마이크로소프트 자체 구성 요소로, 그것도 커널보다 아래 계층까지 넓혀 "Bring Your Own Vulnerable Windows"라는 이름을 붙였습니다.

### 1-3. 완벽한 다운그레이드의 네 가지 조건

본론에 들어가기 전에 성공 기준부터 정의합니다.

| 조건 | 의미 |
| --- | --- |
| Fully Undetectable | 가장 정상적인 방법으로 되돌려서 보안 제품이 막지 못한다 |
| Invisible | 되돌린 뒤에도 시스템은 최신 상태로 보인다 |
| Persistent | 이후 업데이트가 되돌린 상태를 덮어쓰지 못한다 |
| Irreversible | 검사, 복구 도구가 손상을 찾지도 고치지도 못한다 |

이 표가 발표 전체의 뼈대입니다. 뒤에서 기법이 나올 때마다 슬라이드 제목이 이 네 조건 중 하나로 돌아옵니다.

## 승. Windows Update의 설계 결함

### 2-1. 왜 Windows Update인가

윈도우 시스템 파일은 TrustedInstaller라는 별도 권한만 고칠 수 있습니다. 관리자도 직접 덮어쓸 수 없습니다. 관리자에서 이 권한으로 올라가는 방법은 공개돼 있지만, 그런 행동은 보안 제품이 악성으로 잡습니다. 첫 번째 조건과 정면으로 부딪히는 겁니다.

그래서 발표자는 "다운그레이드를 할 거라고 가장 예상하기 어려운 구성 요소"를 고릅니다. Windows Update 자신입니다. 파일을 정상적으로 바꾸는 일이 원래 업데이트의 역할이니, 이 경로로 되돌린다면 이상해 보일 이유가 없습니다.

### 2-2. 검증된 것과 검증되지 않은 것

업데이트 과정을 거칠게 나누면 이렇습니다. 업데이트 파일을 받아 서명과 해시로 검증하고, 검증이 끝나면 "재부팅 때 무엇을 바꿀지" 적은 작업 목록을 만들고, 재부팅할 때 그 목록대로 파일을 교체합니다.

발표자는 먼저 업데이트 파일을 살폈습니다. 일부 파일은 서명이 없어서 빈틈처럼 보였지만, 최종 결과물의 해시가 서명된 파일 안에 박혀 있어서 막혔습니다. 이 막힌 시도를 발표에서 그대로 보여 준 게 좋았습니다. 가장 의심스러운 곳이 왜 안 되는지 먼저 확인하니, 뒤에 나오는 구멍이 운이 아니라 분석의 결과로 들렸습니다.

진짜 구멍은 작업 목록 쪽에 있었습니다. 작업 목록 파일은 보호받고 있었지만, 시스템이 "어느 작업 목록을 처리할지" 기억해 두는 설정값은 보호받지 않았습니다. 관리자라면 이 값을 바꿔 자기가 만든 작업 목록을 가리키게 할 수 있었습니다.

여기서 핵심은 검증 시점입니다. 무결성 검사는 업데이트 파일을 받을 때 일어나고, 작업 목록은 그 뒤에 만들어지니 "이미 검증된 것"으로 취급됩니다. 내용물은 철저히 지켰는데, 내용물이 어디 있는지 가리키는 값은 지키지 않은 셈입니다. 결과적으로 Windows Update가 공격자 대신 파일을 옛 버전으로 되돌려 주고, 수상한 권한 상승은 한 번도 일어나지 않습니다.

### 2-3. 나머지 조건과 검사기 문제

| 조건 | 왜 성립했나 |
| --- | --- |
| Invisible | 무언가를 지운 게 아니라 "업데이트"를 한 것이라 시스템은 최신으로 보입니다 |
| Persistent | 작업 목록을 처리하는 도구가 서명 검증을 받지 않아, 이후 업데이트가 아무것도 바꾸지 못하게 만들 수 있었습니다 |
| Irreversible | 시스템 무결성 검사, 복구 도구 역시 서명 검증을 받지 않아 손상을 못 찾게 만들 수 있었습니다 |

마지막 두 줄이 가장 섬뜩했습니다. 업데이트를 처리하는 도구와 무결성을 검사하는 도구 자체가 검증 대상이 아니었습니다. 검사기를 바꿀 수 있으면 검사 결과는 늘 "이상 없음"입니다.

첫 데모(11:40 무렵)는 이 흐름을 그대로 보여 줍니다. 업데이트 화면에서 "최신 상태"를 확인하고, 패치된 커널 드라이버를 대상으로 한 공격이 실패하는 걸 보여 줍니다. 드라이버를 되돌리고 재부팅하면 같은 공격이 성공하고, 다시 업데이트 화면을 열면 여전히 "최신 상태"입니다.

## 전. VBS까지 흔들리다

### 3-1. 관리자에서 커널은 경계가 아니다

첫 데모는 관리자에서 커널로 올라간 경우입니다. 마이크로소프트 기준으로 이건 보안 경계를 넘은 게 아닙니다. 발표자도 이 점을 먼저 인정합니다. 다만 많은 사용자가 여전히 관리자 계정으로 쓰고 윈도우 기본값도 관리자라서 위협이 사라지지는 않는다고 덧붙입니다.

마이크로소프트가 이 문제에 내놓은 답이 VBS(Virtualization-Based Security)입니다. 커널이 이미 뚫렸다고 가정하고, 하이퍼바이저로 커널보다 더 안쪽에 격리된 공간을 만듭니다. 일반 운영체제가 도는 VTL 0과 보안 기능이 도는 VTL 1로 나누고, 자격 증명을 지키는 Credential Guard나 코드 무결성을 강제하는 HVCI 같은 기능을 VTL 1에 둡니다. VTL 0에서 VTL 1로, 혹은 커널에서 하이퍼바이저로 넘어가는 것은 명확한 보안 경계입니다.

### 3-2. 검증에 실패하면 VBS 없이 부팅

관리자가 설정을 바꿔 VBS를 꺼 버리면 소용이 없으니, VBS에는 "UEFI lock"이라는 보호 장치가 있습니다. 설정을 UEFI 변수에 잠가 두고, 이를 풀려면 부팅 중에 사용자가 물리적으로 승인해야 합니다. 원격 공격자는 끌 수 없다는 전제입니다.

발표자는 VBS를 이루는 핵심 파일이 망가져 있으면 어떻게 되는지 확인했습니다. 복구 모드로 빠질 거라고 예상했는데, 실제로는 부트 로더가 검증에 실패한 뒤 VBS 없이 평소처럼 부팅했습니다. 보호 기능이 실패했을 때 닫히는 게 아니라 열린 쪽으로 넘어간 겁니다(fail-open). 공격자는 VBS를 뚫을 필요 없이 실패하게 만들기만 하면 됐습니다.

이 부분이 발표에서 가장 오래 남았습니다. 복잡한 공격 체인 사이에 아주 단순한 설계 판단 하나가 끼어 있었습니다.

두 번째 데모(19:00 무렵)는 이걸 엮어 가장 엄격한 설정의 PC에서 자격 증명이 빠져나가는 장면을 보여 줍니다. Credential Guard, LSASS 보호, Defender가 모두 켜져 있었고, 재부팅 뒤 전부 무력화됩니다. 업데이트 화면은 이번에도 "최신 상태"입니다.

### 3-3. 보안 경계를 넘는 다운그레이드

발표 후반은 진짜 보안 경계를 다운그레이드로 넘을 수 있는지 하나씩 확인합니다.

| 대상 | 되살린 취약점 | 넘은 경계 |
| --- | --- | --- |
| Credential Guard | CVE-2022-34709 | VTL 0 사용자 모드 → VTL 1 사용자 모드 |
| Secure Kernel | CVE-2021-27090 | VTL 0 사용자 모드 → VTL 1 커널 |
| Hyper-V 하이퍼바이저 | 2년 전 버전으로 되돌림 | VTL 0 사용자 모드 → 하이퍼바이저 |

세 대상 모두 버전 확인이나 폐기 목록 같은 다운그레이드 방지 장치가 없었습니다. 발표자의 판단 기준이 인상적이었습니다. 당장 익스플로잇으로 이어지지 않더라도 방지 장치가 없다는 것 자체를 취약점으로 봤습니다. 앞으로 패치될 취약점이 전부 되살릴 수 있는 무기가 되기 때문입니다.

세 번째 데모(28:00 무렵)에서는 하이퍼바이저가 2년 전 버전으로 돌아간 상태에서도 VBS와 Credential Guard가 아무 일 없다는 듯 계속 돌아갑니다.

### 3-4. 권한 없는 사용자의 경로

마지막으로 관리자 권한이 필요 없는 경로도 나옵니다. 업데이트 후 복원용으로 남겨 두는 옛 운영체제 폴더에 일반 사용자가 전체 권한을 갖고 있었습니다. 폴더 안 파일은 원래 권한을 물려받아 지켜졌지만 폴더 자체는 그렇지 않았습니다. 관리자가 나중에 복원을 실행하면 공격자가 준비한 운영체제가 쓰일 수 있었습니다. 여기서도 내용물은 지켰는데 그걸 담는 그릇은 지키지 않았다는 같은 패턴이 반복됩니다.

### 3-5. 공개 이후

발표자는 2024년 2월 마이크로소프트에 제보했고 CVE-2024-21302, CVE-2024-38202가 발급됐습니다. 대응은 한 번에 끝나지 않았습니다. 2024년 8월 발표 시점에는 CVE-2024-38202 패치가 없었고, 10월에야 배포됐습니다. CVE-2024-21302는 마이크로소프트가 서명한 폐기 정책을 따로 적용해야 하는 방식이라, 관리자가 직접 설정해야 하는 완화책에 가깝습니다.

같은 해 10월 발표자는 후속 연구도 공개했습니다. 마이크로소프트가 관리자에서 커널은 보안 경계가 아니라는 입장이라 이 경로는 막지 않았는데, 이를 이용해 이미 패치된 드라이버 서명 강제 우회를 최신 Windows 11에서 다시 살려 냈습니다. "경계가 아니니 고치지 않는다"는 판단이 실제로 어떤 여지를 남기는지 보여 준 사례입니다. 운영 중인 시스템이 있다면 MSRC의 두 CVE 항목을 직접 확인하는 편이 좋겠습니다.

## 결. 느낀 점과 가져갈 것

### 4-1. 좋았던 점과 아쉬운 점

좋았던 점

- 성공 조건을 먼저 정의하고 하나씩 채워 가는 구성이라 35분 동안 길을 잃지 않습니다.
- 데모가 "최신 상태 확인 → 공격 → 다시 최신 상태 확인"으로 반복돼 메시지가 머리에 박힙니다.
- 무엇이 보안 경계이고 무엇이 아닌지 마이크로소프트 기준으로 짚어 줘서, 결과의 무게를 스스로 가늠할 수 있습니다.

아쉬운 점

1. 대부분의 시나리오가 관리자 권한을 전제로 합니다. 발표자가 이유를 설명하긴 하지만, 위협 모델을 처음 보는 사람에게는 와닿기 어려울 수 있습니다.
2. 하이퍼바이저 부분은 특정 취약점을 직접 보여 주지 않습니다. 2년 전 버전이면 고쳐진 취약점이 하나쯤은 있을 거라는 논리라, 앞의 두 사례보다 근거가 약하게 느껴졌습니다.
3. 방어하는 쪽 이야기가 적습니다. 무엇을 모니터링해야 하는지, 폐기 정책을 언제 적용해야 하는지는 발표 밖에서 찾아야 했습니다.
4. VTL, Secure Kernel 같은 배경이 빠르게 지나갑니다. 윈도우 내부 구조가 처음이라면 슬라이드를 옆에 띄워 두고 보는 걸 추천합니다.

### 4-2. 제 연구와 이어지는 지점

**① ZT-SVF: 정찰하는 공격자는 정상 경로를 고른다**

ZT-SVF에서 공격자는 재인증 정책을 정찰해서 걸리지 않는 위험 상태에 머무릅니다. Windows Downdate의 첫 번째 조건이 정확히 이 생각입니다. 보안 제품이 무엇을 악성으로 보는지 알고, 그 규칙에 걸리지 않는 정상 경로를 골랐습니다. 탐지 규칙이 고정돼 있고 공격자가 그걸 알면 규칙 밖으로 돌아간다는 점에서 같은 구조입니다. 제 논문이 "규칙을 들켜도 이득이 없게" 만드는 쪽으로 간 이유를 운영체제 사례로 다시 확인했습니다.

새로 생긴 질문도 있습니다. ZT-SVF는 위험 상태 `s`가 정해지면 재인증 확률 `p*(s)`를 계산합니다. 그런데 ZTNA는 위험도를 매길 때 흔히 기기 상태, 예를 들어 OS 패치 수준을 신호로 씁니다. Windows Downdate는 그 신호가 거짓말을 하게 만듭니다. 공격자가 이득 함수가 아니라 상태 관측 자체를 속이면 균형 확률이 얼마나 흔들릴까요? MobiSec 질의응답에서 나올 수 있는 질문이라 답을 준비해 두고, 다음 연구 주제 후보로도 적어 둡니다.

**② 증거 게이트웨이: 지킨 것과 가리키는 것**

게이트웨이를 만들 때 해시 체인만으로는 전체 재계산을 못 막는다는 걸 알고, 마지막 해시를 로그와 분리된 곳에 앵커로 남겼습니다. 이번 발표를 보고 두 가지를 다시 점검하게 됐습니다.

- 내용물이 아니라 위치를 가리키는 값. Windows Update는 작업 목록 파일은 지켰지만 "어느 목록을 읽을지"는 지키지 않았습니다. 제 게이트웨이에서 앵커 저장 위치나 검증 키 경로를 정하는 설정이 에이전트가 닿을 수 있는 곳에 있다면, 앵커를 분리한 의미가 사라집니다.
- 검사기 자체의 무결성. 무결성 검사 도구가 서명 검증을 받지 않아 바꿔치기될 수 있었습니다. 검증 CLI를 게이트웨이와 분리하고, 공개키와 앵커만 있으면 제3자가 돌릴 수 있게 만든 결정이 맞았다는 확신이 생겼습니다. 검증은 검증받는 시스템 밖에서 해야 합니다.

**③ DMA 연구: 설계도 공격 표면이다**

발표자의 두 번째 교훈은 "설계도 공격 표면으로 봐야 한다"였습니다. VBS가 검증 실패 시 열린 쪽으로 넘어간 것도, 하위 권한 영역이 상위 권한 영역의 파일을 업데이트할 수 있었던 것도 구현 버그가 아니라 설계 판단이었습니다. 제가 처음 제안한 CPP-DMA의 약점도 코드 실수가 아니라 예측값에 기대는 구조 자체에 있었습니다. 그때 제가 만든 걸 제가 공격해 본 경험이 이 발표를 이해하는 데 그대로 도움이 됐습니다.

### 4-3. 12월 구두발표에 가져갈 것

MobiSec 2026에서 ZT-SVF를 영어로 발표합니다. 이 발표에서 배운 구성 방식을 제 발표에 옮겨 보려고 합니다.

1. **성공 조건을 먼저 보여 주기.** 발표자는 네 가지 조건을 표로 먼저 세우고, 뒤의 슬라이드가 그 표로 계속 돌아오게 했습니다. 저도 "정찰해도 기대이득 0 이하, 학습 단계 없음, 정상 사용자 부담 최소"를 앞에서 요구 조건으로 세우고, 결과 슬라이드마다 어느 조건을 확인하는지 표시하겠습니다.
2. **한 문장을 처음과 끝에 반복하기.** 이 발표는 "fully patched라는 말이 의미를 잃는다"로 시작하고 같은 말로 끝납니다. 제 발표의 한 문장은 "Even if the attacker learns the policy, evasion does not pay."로 잡아 볼 생각입니다.
3. **같은 틀로 비교하기.** 데모 세 개가 모두 같은 화면에서 시작하고 끝나서 차이가 바로 보였습니다. 고정 임계값, DR-TBAC, ZT-SVF 결과를 같은 축의 그래프에 같은 순서로 놓아서, 청중이 그래프 읽는 법을 한 번만 익히면 되게 하겠습니다.
4. **막힌 길도 보여 주기.** 업데이트 파일 쪽이 왜 안 됐는지 먼저 보여 준 덕분에 결과가 설득력 있었습니다. 저도 강화학습 방식이 0과 1로 쏠리며 사각지대가 생기는 장면을 숨기지 않고 넣겠습니다. 제안 방법이 필요한 이유가 그 장면에서 나옵니다.
5. **반박을 먼저 꺼내기.** 발표자는 "관리자에서 커널은 경계가 아니다"라는 반론을 스스로 먼저 꺼내고 답했습니다. 저도 "공격자의 이득과 손실을 방어자가 어떻게 아느냐"는 질문을 먼저 꺼내고, 추정이 틀려도 보장이 선형으로만 약해진다는 분석을 보여 주겠습니다.
6. **핵심 문장은 두 번 말하기.** VBS 우회를 설명할 때 발표자는 "I repeat"라고 하고 같은 문장을 한 번 더 말했습니다. 모국어가 아닌 언어로 발표하는 사람에게 좋은 방법이라고 느꼈습니다. 슬라이드 글자는 줄이고, 꼭 남겨야 할 문장은 말로 두 번 하겠습니다.
7. **열린 질문으로 끝내기.** 마지막 슬라이드는 "리눅스나 macOS는 어떨까" 같은 열린 질문이었습니다. 질의응답이 자연스럽게 그쪽으로 이어졌을 것 같습니다. 저도 ①에서 적은 "상태 관측 자체를 속이면?"을 다음 연구 질문으로 남겨, 대화가 이어질 거리를 만들어 두려고 합니다.

### 4-4. 보고 나서 든 생각

"패치를 다 했으니 안전하다"는 말이 무엇에 기대는지 다시 생각했습니다. 업데이트 기록과 버전 번호는 결국 시스템이 스스로 보고하는 값입니다. 그 보고를 만드는 경로가 오염되면 숫자는 남아도 의미는 없어집니다. 제로트러스트가 "기기가 하는 말을 그대로 믿지 말라"고 할 때 그 말이 얼마나 구체적인 위협을 가리키는지 이번에 실감했습니다.

발표자가 강조한 마지막 교훈도 기억해 두고 싶습니다. BlackLotus라는 실제 공격 사례는 이미 1년 전부터 공개돼 있었고, 그걸 한 단계 일반화했더니 가상화 스택 전체가 영향을 받았습니다. 공격 사례를 보면 "그 취약점이 고쳐졌나"에서 멈추지 말고 "같은 원리가 또 어디에 통할까"를 물어야 한다는 이야기로 받아들였습니다. 연구 주제를 찾는 방법으로도 써먹을 수 있을 것 같습니다 :)

ERC-20 토큰은 서로 구별되지 않습니다. 내 1 USDC와 당신의 1 USDC는 바꿔 써도 상관없고, 컨트랙트가 기록하는 것도 주소별 잔액 하나뿐입니다. 하지만 그림, 게임 아이템, 부동산 증서는 각각이 다른 물건입니다. 이런 자산을 담으려고 나온 표준이 ERC-721입니다.

이 글은 ERC-721이 ERC-20과 어디서 갈라지는지, `safeTransferFrom`과 수신 훅이 왜 생겼는지, 그리고 Bored Ape Yacht Club 컨트랙트에서 표준 인터페이스가 실제로 어떻게 응답하는지를 정리합니다.

## 등장 배경

문서의 동기는 짧습니다. 지갑, 중개인, 경매 앱이 이더리움 위의 어떤 NFT와도 같은 방식으로 대화할 수 있어야 한다는 것입니다. ERC-20이 있어도 이 일은 안 됩니다. ERC-20은 "내 주소가 이 토큰을 몇 개 갖고 있는가"를 답할 뿐이고, 토큰 하나하나가 서로 다른 자산이라는 사실을 표현할 방법이 없습니다.

그래서 ERC-721은 기록 단위를 바꿉니다. 컨트랙트는 `tokenId`마다 소유자를 하나씩 기록합니다. 문서 작성자 중에는 Axiom Zen 이메일을 쓰는 Dieter Shirley가 있습니다. CryptoKitties 컨트랙트(`0x06012c8cf97BEaD5deAe237070F9587f8E7A266d`)의 검증된 소스에도 Axiom Zen과 같은 이름이 적혀 있어서, 이미 돌아가던 수집형 게임의 경험이 표준에 반영되었다고 볼 수 있습니다. 두 기록이 같은 사람을 가리킨다는 것은 이름과 소속 표기가 일치한다는 근거일 뿐 그 이상은 확인하지 않았습니다.

## 인터페이스

필수 인터페이스는 ERC-721과 ERC-165입니다. 핵심 함수는 다음과 같습니다.

| 함수 | 역할 |
|---|---|
| `balanceOf(owner)` | 주소가 가진 토큰 개수 |
| `ownerOf(tokenId)` | 토큰 하나의 소유자 |
| `transferFrom`, `safeTransferFrom` | 토큰 이전 |
| `approve`, `getApproved` | 토큰 하나에 대한 이전 권한 위임 |
| `setApprovalForAll`, `isApprovedForAll` | 내 모든 토큰에 대한 운영자 위임 |

이벤트는 `Transfer`, `Approval`, `ApprovalForAll` 세 가지입니다. `Transfer(from, to, tokenId)`의 시그니처 문자열은 ERC-20의 `Transfer(from, to, value)`와 타입이 같아서 토픽 해시가 같습니다. 구별 기준은 indexed 개수입니다. ERC-721은 `tokenId`까지 indexed라서 로그의 토픽이 4개이고, ERC-20은 3개입니다. 로그를 직접 파싱하는 인덱서를 만든다면 이 점을 놓치기 쉽습니다.

선택 확장도 두 가지 있습니다. `ERC721Metadata`는 `name()`, `symbol()`, `tokenURI(tokenId)`를 더하고, `ERC721Enumerable`은 `totalSupply()`와 인덱스로 토큰을 순회하는 함수를 더합니다.

## safeTransferFrom과 수신 훅

ERC-721에는 이전 함수가 두 종류 있습니다. 검사가 없는 `transferFrom`, 그리고 받는 쪽이 컨트랙트이면 확인을 거치는 `safeTransferFrom`입니다. 받는 주소가 컨트랙트이면 `onERC721Received(operator, from, tokenId, data)`를 호출하고, 반환값이 `0x150b7a02`가 아니면 되돌립니다.

이유는 단순합니다. NFT를 다룰 줄 모르는 컨트랙트로 보내면 영영 꺼낼 수 없습니다. 문서는 반환값을 `true`가 아닌 고정된 매직 값으로 정한 이유도 적어 두었습니다. 오래된 컨트랙트 중에는 함수가 없는데도 우연히 `true`를 돌려주는 경우가 있어서, 명시적인 값으로만 수락을 판단하게 했다는 설명입니다.

## ERC-165

표준 인터페이스를 구현했는지 물어보는 방법이 ERC-165의 `supportsInterface(bytes4)`입니다. ERC-721의 인터페이스 ID는 `0x80ac58cd`, Metadata는 `0x5b5e139f`, Enumerable은 `0x780e9d63`입니다. 마켓플레이스나 지갑은 이 호출로 컨트랙트가 NFT인지, 메타데이터까지 지원하는지 판별합니다.

## 메인넷에서 확인하기

Bored Ape Yacht Club 컨트랙트(`0xBC4CA0EdA7647A8aB7C2061c2E118A18a936f13D`)에 `eth_call`을 보내 봤습니다.

| 호출 | 응답 |
|---|---|
| `name()` | `BoredApeYachtClub` |
| `totalSupply()` | `0x2710`, 10,000 |
| `supportsInterface(0x80ac58cd)` | `true` |

인터페이스 ID가 어디서 나오는지도 직접 계산해 봤습니다. ERC-165의 ID는 인터페이스에 속한 함수 선택자를 모두 XOR한 값입니다. ERC-721의 함수 9개(`balanceOf`부터 `isApprovedForAll`까지, `safeTransferFrom`은 두 오버로드를 따로 계산)를 XOR하자 `0x80ac58cd`가, Metadata의 세 함수에서는 `0x5b5e139f`가 나왔습니다. `onERC721Received(address,address,uint256,bytes)`의 선택자도 문서의 `0x150b7a02`와 같았습니다.

로그 구조도 확인했습니다. BAYC의 최근 2,000블록 안에서 `Transfer` 로그 16건을 찾았고, 그중 마지막 로그는 topic이 4개이며 data가 비어 있었습니다. 보내는 주소, 받는 주소, `tokenId`가 모두 indexed라서 data에 남는 값이 없는 것입니다. 같은 시그니처인 USDC의 `Transfer`(최근 300블록에서 13,777건)는 topic이 3개이고 금액이 data에 실려 있었습니다. 앞에서 말한 구별 기준이 실제 로그에서 그대로 보입니다.

세 줄이지만 표준이 하는 일이 다 들어 있습니다. 호출하는 쪽은 BAYC를 따로 알 필요가 없고, 선택 확장인 `name()`과 `totalSupply()`가 표준 시그니처로 응답하며, ERC-165 질의로 이 컨트랙트가 ERC-721임을 확인할 수 있습니다. 직접 해 보려면 Foundry의 `cast`를 쓰면 됩니다.

```bash
cast call 0xBC4CA0EdA7647A8aB7C2061c2E118A18a936f13D \
  "supportsInterface(bytes4)(bool)" 0x80ac58cd --rpc-url https://ethereum-rpc.publicnode.com
```

## 구현해 보기

OpenZeppelin v5를 쓰면 구현은 짧습니다. 아래 코드는 solc 0.8.26과 OpenZeppelin Contracts 5.6.1로 컴파일되는 것을 확인했습니다. 배포하거나 민팅을 실행해 보는 테스트는 하지 않았습니다. 테스트 네트워크와 가스를 낼 계정이 있어야 하는데 이번에 준비하지 않았습니다.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import {ERC721} from "@openzeppelin/contracts/token/ERC721/ERC721.sol";
import {Ownable} from "@openzeppelin/contracts/access/Ownable.sol";

contract MyNFT is ERC721, Ownable {
    uint256 private _nextId;

    constructor() ERC721("MyNFT", "MNFT") Ownable(msg.sender) {}

    function mint(address to) external onlyOwner returns (uint256 id) {
        id = _nextId++;
        _safeMint(to, id); // 받는 쪽이 컨트랙트면 onERC721Received를 호출
    }
}
```

## 한계와 주의할 점

`setApprovalForAll`은 편리한 만큼 위험합니다. 마켓플레이스에 거래 권한을 주려면 컬렉션 전체에 대한 운영자 승인이 필요한데, 피싱 사이트가 같은 서명을 받아 가면 컬렉션의 모든 토큰을 옮길 수 있습니다. 승인 화면에서 운영자 주소를 확인하는 습관이 필요합니다.

`_safeMint`와 `safeTransferFrom`은 받는 컨트랙트의 코드를 호출합니다. 상태 변경이 끝나기 전에 훅이 실행되면 재진입 공격 경로가 됩니다. 민팅 수량 제한이나 결제 로직을 훅 호출 앞에서 마무리하거나 재진입 방지를 붙여야 합니다.

`tokenURI`가 가리키는 메타데이터와 이미지는 대부분 체인 밖에 있습니다. 소유권 기록은 이더리움에 영구적으로 남아도, 이미지가 올라간 서버나 IPFS 핀이 사라지면 토큰이 가리키는 그림은 사라질 수 있습니다. 표준은 소유권 이전만 정하고 그 이후는 정하지 않습니다.

## 정리

ERC-721의 핵심은 `tokenId`마다 소유자를 기록한다는 점과, 받는 쪽을 확인하는 `safeTransferFrom`, 인터페이스를 질의하는 ERC-165입니다. BAYC 컨트랙트에서 세 호출만으로 이 구조를 확인했습니다. 다음 글에서는 ERC-20 쪽의 불편함을 서명 하나로 풀어낸 [ERC-2612](/posts/erc-2612-permit/)를 다룹니다.

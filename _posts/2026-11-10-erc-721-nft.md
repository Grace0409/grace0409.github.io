ERC-20 토큰은 서로 구별되지 않습니다. 내 1 USDC와 당신의 1 USDC는 바꿔 써도 되고, 컨트랙트가 적어 두는 것도 주소별 잔액 하나뿐입니다. 반면 그림, 게임 아이템, 부동산 증서는 하나하나가 다른 물건입니다. 이런 자산을 담으려고 나온 표준이 ERC-721입니다.

## ERC-20과 다른 점

ERC-20은 주소가 토큰을 몇 개 갖고 있는지만 기록합니다. ERC-721은 `tokenId`마다 소유자를 한 명씩 기록합니다. 표준이 필요했던 이유는 지갑, 중개인, 경매 앱이 어떤 NFT든 같은 방식으로 다루게 하려는 것입니다.

문서 작성자 중에는 Axiom Zen 이메일을 쓰는 Dieter Shirley가 있습니다. 수집형 게임 CryptoKitties의 컨트랙트(`0x06012c8cf97BEaD5deAe237070F9587f8E7A266d`) 검증된 소스에도 Axiom Zen과 Dieter Shirley라는 이름이 적혀 있습니다. 이미 돌아가던 게임의 경험이 표준에 반영됐을 것으로 짐작하지만, 확인한 것은 이름과 소속이 일치한다는 점까지입니다.

## 핵심 함수

| 함수 | 하는 일 |
|---|---|
| `balanceOf(owner)` | 주소가 가진 토큰 개수 |
| `ownerOf(tokenId)` | 토큰 하나의 소유자 |
| `transferFrom`, `safeTransferFrom` | 토큰 이전 |
| `approve`, `getApproved` | 토큰 하나에 대한 이전 권한을 남에게 맡김 |
| `setApprovalForAll`, `isApprovedForAll` | 내 모든 토큰에 대한 권한을 운영자에게 맡김 |

이벤트는 `Transfer`, `Approval`, `ApprovalForAll` 세 가지입니다. ERC-721의 `Transfer`는 ERC-20의 `Transfer`와 이름과 인자 타입이 같아서 이벤트 해시도 같습니다. 구별하는 방법은 indexed 인자의 개수입니다. ERC-721은 `tokenId`까지 indexed라서 로그의 topic이 4개이고, ERC-20은 3개입니다. 로그를 직접 읽는 프로그램을 만든다면 이 차이를 알고 있어야 합니다.

## safeTransferFrom이 따로 있는 이유

`transferFrom`은 받는 쪽을 확인하지 않습니다. NFT를 다룰 줄 모르는 컨트랙트로 보내면 영영 꺼낼 수 없습니다. `safeTransferFrom`은 받는 주소가 컨트랙트일 때 그 컨트랙트의 `onERC721Received`를 불러, 약속된 값(`0x150b7a02`)이 돌아와야만 이전을 끝냅니다.

문서에는 `true`가 아니라 고정된 값을 쓰는 이유도 적혀 있습니다. 오래된 컨트랙트 중에는 함수가 없는데도 우연히 `true`를 돌려주는 경우가 있어서, 정해진 값일 때만 받도록 정했다고 합니다.

## ERC-165, 인터페이스 지원 여부 확인

`supportsInterface(bytes4)`를 부르면 컨트랙트가 그 인터페이스를 지원하는지 답합니다. ERC-721의 인터페이스 ID는 `0x80ac58cd`, Metadata 확장은 `0x5b5e139f`, Enumerable 확장은 `0x780e9d63`입니다. 마켓플레이스나 지갑이 이 호출로 컨트랙트가 NFT인지 확인합니다.

## BAYC 컨트랙트 확인

Bored Ape Yacht Club(BAYC) 컨트랙트(`0xBC4CA0EdA7647A8aB7C2061c2E118A18a936f13D`)에 `eth_call`을 보내 봤습니다.

| 호출 | 응답 |
|---|---|
| `name()` | `BoredApeYachtClub` |
| `totalSupply()` | `0x2710`, 곧 10,000 |
| `supportsInterface(0x80ac58cd)` | `true` |

BAYC를 따로 몰라도 표준 함수만 부르면 이름, 발행량, ERC-721 지원 여부를 알 수 있습니다. 같은 호출은 Foundry의 `cast`로 해 볼 수 있습니다.

```bash
cast call 0xBC4CA0EdA7647A8aB7C2061c2E118A18a936f13D \
  "supportsInterface(bytes4)(bool)" 0x80ac58cd --rpc-url https://ethereum-rpc.publicnode.com
```

인터페이스 ID가 어디서 나오는지도 계산해 봤습니다. ID는 인터페이스에 속한 함수들의 선택자(함수 이름을 해시한 앞 4바이트)를 모두 XOR한 값입니다. ERC-721의 함수 9개(`safeTransferFrom`은 오버로드 두 개를 따로 계산)를 XOR하니 `0x80ac58cd`가, Metadata의 세 함수에서는 `0x5b5e139f`가 나왔습니다. `onERC721Received`의 선택자도 문서의 `0x150b7a02`와 같았습니다.

로그도 열어 봤습니다. BAYC의 최근 2,000블록에서 `Transfer` 로그 16건을 찾았고, 그중 마지막 로그는 topic이 4개이고 data가 비어 있었습니다. 보낸 주소, 받은 주소, `tokenId`가 모두 topic에 들어가기 때문입니다. 같은 이벤트인 USDC의 `Transfer`(최근 300블록에서 13,777건)는 topic이 3개이고 금액이 data에 있었습니다.

## 구현 예시

OpenZeppelin v5를 쓰면 구현이 짧습니다. 아래 코드는 solc 0.8.26과 OpenZeppelin Contracts 5.6.1로 컴파일되는 것까지 확인했습니다.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import {ERC721} from "@openzeppelin/contracts/token/ERC721/ERC721.sol";
import {Ownable} from "@openzeppelin/contracts/access/Ownable.sol";

contract MyNFT is ERC721, Ownable {
    uint256 private _nextId;

    constructor() ERC721("MyNFT", "MNFT") Ownable(msg.sender) {}

    function mint(address to) external onlyOwner returns (uint256 id) {
        id = _nextId++;
        _safeMint(to, id); // 받는 쪽이 컨트랙트면 onERC721Received를 호출
    }
}
```

## 조심할 점

1. `setApprovalForAll`은 편한 만큼 위험합니다. 마켓플레이스에 거래 권한을 주려면 컬렉션 전체에 대한 운영자 승인이 필요한데, 피싱 사이트가 같은 승인 트랜잭션에 서명하도록 유도하면 컬렉션의 모든 토큰을 옮길 수 있습니다. 승인 화면에서 운영자 주소를 확인하는 습관이 필요합니다.
2. `_safeMint`와 `safeTransferFrom`은 받는 컨트랙트의 코드를 부릅니다. 상태 변경이 끝나기 전에 그 코드가 실행되면 재진입 공격의 통로가 됩니다. 민팅 수량 제한이나 결제 로직은 훅을 부르기 전에 끝내거나 재진입 방지를 붙여야 합니다.
3. `tokenURI`가 가리키는 이미지와 설명은 대부분 체인 밖에 있습니다. 소유 기록은 이더리움에 남아도, 이미지가 올라간 서버가 없어지면 토큰이 가리키는 그림은 사라질 수 있습니다.

## 확인하지 못한 것

위 컨트랙트를 배포하거나 민팅을 실행해 보지는 못했습니다. 테스트 네트워크와 가스를 낼 계정이 필요한데 준비하지 않았습니다.

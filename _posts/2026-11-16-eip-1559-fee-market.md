가스 가격을 직접 입찰하던 시절이 있었습니다. 지갑에서 느림, 보통, 빠름 중 하나를 고르고, 그래도 안 들어가면 같은 nonce로 더 높은 가격의 트랜잭션을 다시 보내곤 했습니다. 2021년 8월 5일 London 하드포크 이후로 이 과정이 많이 바뀌었고, 바뀐 이유가 EIP-1559입니다.

이 글에서는 EIP-1559가 어떤 문제를 풀려고 나왔는지, 규칙이 어떻게 생겼는지, 그리고 London 첫 블록과 오늘 메인넷 블록에서 그 규칙이 실제로 돌아가는 모습을 정리합니다. 수치는 모두 공개 RPC로 직접 조회한 값입니다 :)

## 등장 배경

EIP-1559 이전의 수수료는 단순한 경매였습니다. 사용자가 가스 가격을 써서 내면, 채굴자는 높은 가격부터 골라 블록에 넣고, 포함된 트랜잭션은 자기가 쓴 가격을 그대로 냈습니다. EIP 문서는 이 방식의 문제를 네 가지로 짚습니다.

첫째는 수수료의 출렁임입니다. 블록 하나에 트랜잭션 하나를 더 넣을 때 네트워크가 치르는 비용은 가스 가격이 1 nanoeth일 때나 10 nanoeth일 때나 거의 같습니다. 그런데 가격은 열 배씩 뛰었습니다. 둘째는 불필요한 대기입니다. 블록 크기가 고정되어 있어서, 수요가 잠깐 몰리면 트랜잭션이 여러 블록을 기다렸습니다. 셋째는 최고가 입찰 방식 자체의 비효율입니다. 다들 얼마를 써야 포함될지 몰라서 넉넉하게 쓰고, 그 결과 수수료를 과하게 냅니다. 넷째는 장기적인 안정성으로, 블록 보상이 줄어들고 수수료만 남는 체인은 불안정해질 수 있다는 논의입니다.

## 핵심 규칙

EIP-1559는 수수료를 두 조각으로 나눕니다.

base fee는 프로토콜이 블록마다 정하는 가스당 가격입니다. 누구에게도 지급되지 않고 소각됩니다. priority fee는 블록을 만드는 쪽에 주는 팁입니다. 사용자는 여기에 상한을 하나 더 붙입니다. 이것이 max fee입니다.

트랜잭션 타입 0x02에는 이 둘이 필드로 들어갑니다. 필드 이름은 `max_priority_fee_per_gas`와 `max_fee_per_gas`입니다. 실제로 내는 가스당 가격은 아래와 같이 정해집니다.

```text
priority_fee = min(max_priority_fee_per_gas, max_fee_per_gas - base_fee)
실제 가스 가격 = base_fee + priority_fee
```

숫자로 한번 따라가 보겠습니다. 아래는 제가 가정한 예이고, 실제 거래 기록은 아닙니다. max fee 50 gwei, priority fee 2 gwei로 보냈는데 블록의 base fee가 30 gwei였다면 가스당 32 gwei를 냅니다. 상한 50 gwei와의 차이 18 gwei는 청구되지 않습니다. 21,000 gas짜리 단순 송금이라면 총 672,000 gwei(0.000672 ETH)가 나가고, 그중 630,000 gwei가 소각되며 42,000 gwei가 팁으로 갑니다.

## base fee가 움직이는 방식

base fee는 직전 블록이 얼마나 찼는지로 정해집니다. 기준은 gas target이고, 이는 블록 gas limit을 ELASTICITY_MULTIPLIER(2)로 나눈 값입니다. 직전 블록이 target보다 가득 찼으면 오르고, 덜 찼으면 내립니다. 한 블록에서 움직일 수 있는 폭은 BASE_FEE_MAX_CHANGE_DENOMINATOR(8) 때문에 최대 1/8, 즉 12.5%입니다.

그래서 블록은 target의 두 배까지 찰 수 있습니다. 수요가 잠깐 몰리면 블록이 커져서 흡수하고, 몰림이 이어지면 가격이 올라 수요를 누르는 구조입니다. 문서의 참조 구현을 정수 연산으로 옮기면 이렇습니다.

```js
// 다음 블록의 base fee (EIP-1559 참조 구현을 옮긴 것, 오를 때 최소 1 wei)
function nextBaseFee(parentBase, parentGasLimit, parentGasUsed) {
  const target = parentGasLimit / 2n;
  if (parentGasUsed === target) return parentBase;
  if (parentGasUsed > target) {
    const delta = (parentBase * (parentGasUsed - target)) / target / 8n;
    return parentBase + (delta > 1n ? delta : 1n);
  }
  const delta = (parentBase * (target - parentGasUsed)) / target / 8n;
  return parentBase - delta;
}
```

## 메인넷에서 확인하기

London의 첫 블록은 12,965,000번입니다. 바로 앞 블록과 이후 몇 블록을 조회했습니다.

| 블록 | 시각(UTC) | gasLimit | gasUsed | baseFeePerGas |
|---|---|---|---|---|
| 12,964,999 | 2021-08-05 12:33:32 | 15,029,237 | 15,026,712 | 없음 |
| 12,965,000 | 2021-08-05 12:33:42 | 30,029,122 | 30,025,257 | 1 gwei |
| 12,965,001 | 2021-08-05 12:33:55 | 29,999,798 | 29,985,144 | 1.124967822 gwei |
| 12,965,002 | 2021-08-05 12:34:14 | 29,970,503 | 29,950,343 | 1.265451421 gwei |

두 가지가 눈에 띕니다. 포크 직전 블록에는 base fee 필드가 아예 없고, 포크 블록에서 gasLimit이 15.03M에서 30.03M으로 두 배가 됩니다. target은 그대로 약 15M에 두고, 블록이 target의 두 배까지 찰 수 있게 한도를 넓힌 것입니다. 첫 블록의 base fee는 EIP가 정한 INITIAL_BASE_FEE, 즉 1 gwei로 시작합니다.

그 뒤로는 블록이 거의 가득 찬 상태가 이어져서 base fee가 두 블록 연속으로 12.5%에 가깝게 올랐습니다. 위의 `nextBaseFee`에 이 값들을 넣어 보면 12,965,001번은 1124967822 wei, 12,965,002번은 1265451421 wei로 나오고, 둘 다 관측값과 한 자리도 다르지 않았습니다.

오늘 상태도 봤습니다. 2026년 11월 15일 17:49:59 UTC의 최신 블록(26,422,007번)은 base fee가 약 0.181 gwei, gasLimit이 60,000,000, gasUsed가 51,107,427이었습니다. gasLimit이 London 때의 두 배가 되었고, 블록은 target(30M)을 웃돌게 차 있으니 다음 블록 base fee는 오르는 방향입니다.

최근 10개 블록의 트랜잭션 3,207건을 타입별로 세어 보면 아래와 같습니다. 한 시점의 표본이라는 점은 감안해 주세요.

| 타입 | 건수 | 비율 |
|---|---|---|
| 0x2 (EIP-1559) | 2,847 | 88.8% |
| 0x0 (레거시) | 298 | 9.3% |
| 0x3 (blob) | 23 | 0.7% |
| 0x4 (EIP-7702) | 39 | 1.2% |

레거시 트랜잭션은 지금도 처리됩니다. 이때는 `gas_price` 전체가 max fee이자 max priority fee로 해석되고, base fee를 먼저 채운 나머지가 팁이 됩니다. 새 타입이 나온 뒤에도 이전 지갑과 스크립트가 깨지지 않은 이유입니다.

## 쓰는 방법

개발자가 직접 건드리는 곳은 많지 않습니다. ethers v6에서는 대략 이런 모양입니다.

```js
const fee = await provider.getFeeData();
// fee.maxFeePerGas, fee.maxPriorityFeePerGas는 노드의 fee history를 바탕으로 한 추정치
await signer.sendTransaction({
  to,
  value,
  maxFeePerGas: fee.maxFeePerGas,
  maxPriorityFeePerGas: fee.maxPriorityFeePerGas,
});
```

컨트랙트 안에서는 `block.basefee`로 현재 블록의 base fee를 읽을 수 있습니다. 이 opcode는 London에서 EIP-3198로 함께 들어왔습니다. blob 데이터에 붙는 수수료(EIP-4844)도 별도의 base fee를 두고 수요에 따라 조정하는 같은 발상을 씁니다. 위 표에서 타입 0x3 트랜잭션이 따로 잡히는 이유이기도 합니다.

## 한계와 주의할 점

EIP-1559가 평균 수수료를 낮추는 장치는 아닙니다. 수요가 길게 몰리면 base fee도 블록마다 12.5%씩 복리로 올라갑니다. 달라진 것은 예측 가능성입니다. 다음 블록의 base fee 범위가 직전 블록만으로 정해지니 지갑이 가격을 자동으로 잡아 줄 수 있습니다.

팁이 사라진 것도 아닙니다. 급하게 포함되고 싶다면 priority fee를 올려야 합니다. max fee를 너무 낮게 잡으면 base fee가 올랐을 때 트랜잭션이 pending 상태로 남습니다.

소각이 ETH 공급량에 얼마나 영향을 주는지는 이 글에서 직접 집계하지 않았습니다. 문서가 밝힌 의도는 base fee 소각으로 블록 생성자가 수수료를 조작할 유인을 없애고, ETH만이 수수료 수단이 되도록 하는 것입니다. 소각 규모를 알고 싶다면 별도의 대시보드나 블록 데이터를 집계해야 합니다.

## 정리

EIP-1559는 "얼마를 써야 들어갈까"를 사용자가 맞히는 경매에서 프로토콜이 base fee를 제시하는 구조로 옮겼습니다. London 첫 블록의 1 gwei에서 출발한 base fee는 공식 그대로 움직였고, 지금 메인넷 트랜잭션의 대부분이 이 타입입니다. 다음 글에서는 토큰 쪽으로 넘어가 [ERC-721](/posts/erc-721-nft/)을 다룹니다.

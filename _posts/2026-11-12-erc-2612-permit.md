DEX에서 토큰을 처음 교환하려고 하면 지갑 창이 두 번 뜹니다. 한 번은 "이 컨트랙트가 내 토큰을 쓰도록 허용"하는 `approve`, 한 번은 실제 교환입니다. 둘 다 트랜잭션이라서 가스비가 두 번 나가고, 첫 단계에서 기다려야 합니다. ERC-2612는 이 첫 단계를 오프체인 서명으로 바꿉니다.

이 글에서는 `permit`이 왜 필요했는지, 서명이 어떤 구조인지, USDC와 DAI에서 어떻게 달라 보이는지, 그리고 쓸 때 조심해야 할 점을 정리합니다.

## 등장 배경

ERC-20의 `approve(spender, amount)`는 `msg.sender`가 허용을 거는 함수입니다. 컨트랙트를 거쳐 토큰을 쓰려면 사용자가 먼저 EOA로 트랜잭션을 보내야 한다는 뜻입니다. 두 가지 불편이 따라옵니다.

하나는 트랜잭션이 두 번 필요하다는 점입니다. `approve`가 끝난 뒤에야 실제 호출이 가능합니다. 다른 하나는 토큰만 갖고 ETH가 없는 사용자는 시작조차 못 한다는 점입니다. 이 불편을 풀려는 제안은 여러 번 있었지만, EIP 문서가 짚듯 EIP-777처럼 기능을 크게 얹은 방식은 주류 컨트랙트에서 예상 밖의 동작을 만들었습니다.

ERC-2612는 범위를 좁게 잡았습니다. 문제는 오직 `approve`가 `msg.sender`에 묶여 있다는 것이니, 그 부분만 서명으로 대체합니다. `transfer`의 서명 버전 같은 건 일부러 넣지 않았습니다. 수수료 구조나 배치 방식이 용도마다 다르고, `permit`과 보조 컨트랙트를 조합하면 만들 수 있기 때문입니다.

## 인터페이스

ERC-20에 세 함수가 추가됩니다.

```solidity
function permit(address owner, address spender, uint value, uint deadline, uint8 v, bytes32 r, bytes32 s) external
function nonces(address owner) external view returns (uint)
function DOMAIN_SEPARATOR() external view returns (bytes32)
```

`permit`은 유효한 서명이 있을 때 `allowance[owner][spender]`를 `value`로 바꾸고, `nonces[owner]`를 1 올리며, `Approval` 이벤트를 냅니다. 조건은 네 가지입니다. 현재 시각이 `deadline` 이하일 것, `owner`가 0 주소가 아닐 것, 서명한 nonce가 현재 `nonces[owner]`와 같을 것, 그리고 `owner`가 서명한 올바른 secp256k1 서명일 것입니다. 하나라도 어기면 되돌립니다.

서명 대상은 EIP-712 구조화 데이터입니다.

```text
Permit(address owner, address spender, uint256 value, uint256 nonce, uint256 deadline)
```

`DOMAIN_SEPARATOR`에는 토큰 이름, 버전, `chainId`, 컨트랙트 주소가 들어갑니다. 덕분에 같은 서명을 다른 체인이나 다른 토큰에서 재사용할 수 없습니다. 지갑은 이 구조를 읽어 "이 사이트가 USDC 얼마를 쓰도록 허용합니다"처럼 사람이 읽을 수 있는 형태로 보여줄 수 있습니다. 해시된 바이트 덩어리를 서명하라고 요구하던 방식과 비교하면 큰 차이입니다.

## 흐름

1. 사용자가 지갑으로 `Permit` 메시지에 서명합니다. 트랜잭션이 아니라서 가스비가 들지 않습니다.
2. 앱이 서명을 받아 컨트랙트 호출에 같이 실어 보냅니다.
3. 컨트랙트가 토큰의 `permit`을 부르고, 이어서 `transferFrom`으로 토큰을 가져갑니다. 이 모두가 트랜잭션 한 번 안에서 일어납니다.

서명한 뒤 트랜잭션을 보내는 사람은 사용자가 아니어도 됩니다. 그래서 ETH가 없는 사용자의 가스를 앱이나 릴레이어가 대신 내주는 설계도 가능합니다.

## 메인넷에서 확인하기

USDC(`0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48`)에 `eth_call`을 보내 봤습니다.

| 호출 | 응답 |
|---|---|
| `name()` | `USD Coin` |
| `version()` | `2` |
| `PERMIT_TYPEHASH()` | `0x6e71edae12b1b97f4d1f60370fef10105fa2faae0126114a169c64845d6126c9` |
| `DOMAIN_SEPARATOR()` | `0x06c37168a7db5138defc7866392bb87a741f9b3d104deb5094588ce041cae335` |
| `nonces(0x…01)` | `0` |

응답을 믿기만 하지 않고 직접 해시를 계산해 맞춰 봤습니다. 문서의 `Permit(address owner,address spender,uint256 value,uint256 nonce,uint256 deadline)` 문자열을 keccak256으로 해시하면 USDC가 돌려준 `PERMIT_TYPEHASH`와 정확히 같습니다. `DOMAIN_SEPARATOR`는 `EIP712Domain` 타입 해시에 이름 `USD Coin`, 버전 `2`, `chainId` 1, USDC 주소를 이어 붙여 해시했고, 이 역시 온체인 값과 일치했습니다. 곧 USDC가 ERC-2612 구조 그대로 서명을 검증한다는 뜻입니다.

DAI(`0x6B175474E89094C44Da98b954EedeAC495271d0F`)는 다릅니다. 같은 이름의 `permit`이 있고 `DOMAIN_SEPARATOR`도 응답하지만 `PERMIT_TYPEHASH`는 `0xea2aa0a1be11a07ed86d755c93467f4f82362b452371d1ba94d1715123511acb`로 다릅니다. DAI 컨트랙트는 2019년 11월 13일에 배포되었고 ERC-2612는 2020년 4월 13일에 작성되었으니(문서 머리말 기준), DAI의 `permit`은 ERC-2612보다 먼저 나온 방식이고 서명 구조가 `holder`, `spender`, `nonce`, `expiry`, `allowed`로 되어 있습니다. `Permit(address holder,address spender,uint256 nonce,uint256 expiry,bool allowed)`를 해시하면 위의 DAI typehash가 나오고, 이름 `Dai Stablecoin`과 버전 `1`로 계산한 `DOMAIN_SEPARATOR`도 온체인 값과 같았습니다. 금액 대신 허용 여부를 true와 false로 다룹니다. 앱 입장에서는 `permit`이 있다고 해서 같은 코드로 서명을 만들 수 없다는 뜻입니다.

토큰 자체에 `permit`이 없을 때를 위한 해법도 메인넷에 올라와 있습니다. Permit2(`0x000000000022D473030F116dDEE9F6B43aC78BA3`, 흔히 Uniswap이 만든 것으로 알려져 있습니다)는 서명으로 토큰 이동을 처리하는 별도의 컨트랙트입니다. 검증된 소스의 주석은 "서명 기반 전송은 SignatureTransfer에서, 허용량 기반 전송은 AllowanceTransfer에서 처리한다"고 설명합니다. ABI에는 `permit`, `permitTransferFrom`, `permitWitnessTransferFrom`, `allowance`, `approve`, `transferFrom`, `invalidateNonces`, `lockdown` 같은 함수가 있었고, 코드 크기는 9,152 바이트였습니다.

여기까지는 소스의 주석과 ABI를 읽은 결과입니다. 내부 로직을 끝까지 추적하거나 Permit2로 실제 전송을 해 보지는 않았습니다. 제작 주체도 소스에서 직접 확인하지 못했습니다. 소스에는 Uniswap v2 코드를 수정했다는 표기만 있었습니다. 앱이 Permit2를 쓰려면 사용자가 토큰마다 Permit2에 먼저 한 번 `approve`를 해야 한다는 점도 이번에 실행으로 확인하지는 못했습니다.

## 서명 만들기

ethers v6로 USDC에 대한 서명을 만드는 예입니다.

```js
import { ethers } from "ethers";

const domain = {
  name: "USD Coin",
  version: "2",
  chainId: 1,
  verifyingContract: "0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48",
};
const types = {
  Permit: [
    { name: "owner", type: "address" },
    { name: "spender", type: "address" },
    { name: "value", type: "uint256" },
    { name: "nonce", type: "uint256" },
    { name: "deadline", type: "uint256" },
  ],
};
const owner = await signer.getAddress();
const message = {
  owner,
  spender,                         // 토큰을 쓸 컨트랙트
  value: 1_000_000n,               // USDC는 소수점 6자리, 1 USDC
  nonce: await usdc.nonces(owner), // 컨트랙트에서 읽은 현재 nonce
  deadline: Math.floor(Date.now() / 1000) + 600,
};
const sig = ethers.Signature.from(await signer.signTypedData(domain, types, message));
// sig.v, sig.r, sig.s를 permit 호출에 그대로 넘깁니다.
```

### 실제 USDC로 시험하기

서명 구조가 실제로 통하는지도 메인넷 USDC에 시험해 봤습니다. 잔액이 없는 임시 키를 새로 만들고(USDC 잔액 0, nonce 0), 위와 같은 도메인과 타입으로 서명한 뒤 USDC의 `permit`을 `eth_call`로 호출했습니다. `eth_call`은 노드에서 시뮬레이션만 하고 블록에 기록하지 않아서 온체인에는 아무것도 남지 않습니다.

| 호출 | 결과 |
|---|---|
| 올바른 서명 (v=28) | 성공 |
| 같은 서명을 v=27로 호출 | `EIP2612: invalid signature`로 거부 |
| value를 1만 바꾼 서명 | `EIP2612: invalid signature`로 거부 |
| deadline을 과거로 바꾼 호출 | `FiatTokenV2: permit is expired`로 거부 |

v가 27과 28 중 하나만 통과하는 것은 서명에서 서명자의 공개키를 복구할 때 쓰는 값이어서입니다. 값이 한 글자만 어긋나도 거부되는 것이 보입니다.

이 시험은 위의 ethers 코드를 실행한 것이 아닙니다. 라이브러리를 설치하지 않아서, 같은 도메인과 타입 구조를 직접 구현한 secp256k1 서명으로 만들어 시험했습니다. 그러므로 확인된 것은 "이 서명 데이터의 구조를 USDC가 받아 준다"이고, ethers의 호출 방식이 맞는지는 별도로 실행해 봐야 합니다.

## 컨트랙트에서 쓰기

받는 쪽 컨트랙트는 `permit`과 `transferFrom`을 이어서 부릅니다. 아래 코드는 solc 0.8.26과 OpenZeppelin Contracts 5.6.1로 컴파일되는 것을 확인했습니다. 배포하거나 실제 토큰으로 호출해 보지는 못했습니다.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";
import {IERC20Permit} from "@openzeppelin/contracts/token/ERC20/extensions/IERC20Permit.sol";
import {SafeERC20} from "@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol";

contract PermitVault {
    function depositWithPermit(
        address token, uint256 amount, uint256 deadline,
        uint8 v, bytes32 r, bytes32 s
    ) external {
        // permit이 이미 실행됐을 수 있으니 실패를 허용하고 allowance로 다시 확인
        try IERC20Permit(token).permit(msg.sender, address(this), amount, deadline, v, r, s) {} catch {}
        require(IERC20(token).allowance(msg.sender, address(this)) >= amount, "no allowance");
        SafeERC20.safeTransferFrom(IERC20(token), msg.sender, address(this), amount);
    }
}
```

`try/catch`가 들어간 이유는 아래 한계에서 설명합니다.

## 한계와 주의할 점

첫째는 서명 선점(front-running)입니다. 서명은 트랜잭션 안에 담기는 순간 멤풀에 공개됩니다. 누군가 같은 서명으로 `permit`만 먼저 실행해 버리면 nonce가 소진되어 사용자의 원래 트랜잭션이 되돌려집니다. 공격자가 얻는 이득은 없지만 호출을 방해할 수 있습니다. 위 예시처럼 `permit` 실패를 허용하고 `allowance`를 다시 확인하는 방식이 통상적인 대응입니다.

둘째는 피싱입니다. `permit` 서명은 트랜잭션이 아니라서 지갑에 가스 추정이나 전송 확인 화면이 뜨지 않습니다. 서명 한 번이 곧 토큰 사용 권한이 되므로, 서명창에서 `spender`와 `value`, `deadline`을 읽는 습관이 중요합니다. 금액을 무제한으로 쓰는 서명은 특히 조심해야 합니다.

셋째는 스마트 컨트랙트 지갑입니다. ERC-2612는 `ecrecover`로 EOA의 서명을 검증하는 방식이라, 서명 검증을 컨트랙트가 직접 하는 지갑(ERC-1271 방식)은 이 서명을 만들 수 없습니다. 다음 글에서 다룰 [ERC-4337](/posts/erc-4337-account-abstraction/) 중 컨트랙트로 배포한 계정이 이 경우에 해당합니다. EOA에 코드를 위임한 7702 계정은 개인키가 그대로 있어서 EOA 서명을 만들 수 있습니다.

넷째는 도메인입니다. `DOMAIN_SEPARATOR`에는 `chainId`가 들어갑니다. 체인이 갈라졌을 때 이전 체인의 값을 캐시해서 쓰면 다른 체인의 서명을 받아들일 수 있습니다. 구현이 `chainId` 변화를 확인하고 다시 계산하는지 보는 것이 안전합니다.

## 정리

ERC-2612는 ERC-20에서 딱 한 가지, `approve`의 `msg.sender` 의존만 없앴습니다. USDC의 `PERMIT_TYPEHASH`와 `DOMAIN_SEPARATOR`를 읽어 직접 계산한 값과 맞춰 봤고, DAI가 다른 typehash를 쓰는 것도 같은 방식으로 확인했습니다. 서명은 편하지만 한 번의 서명이 곧 권한이라서, 앱을 만드는 쪽은 선점 대응을, 쓰는 쪽은 서명 내용 확인을 꼭 챙겨야 합니다.

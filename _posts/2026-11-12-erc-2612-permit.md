DEX에서 토큰을 처음 교환하려고 하면 지갑 창이 두 번 뜹니다. 한 번은 이 컨트랙트가 내 토큰을 써도 된다고 허락하는 `approve`, 한 번은 실제 교환입니다. 둘 다 트랜잭션이라서 가스비가 두 번 나가고, 첫 번째가 끝나기를 기다려야 합니다. ERC-2612는 첫 단계를 서명으로 바꿔 이 번거로움을 줄입니다.

## 왜 필요했나

ERC-20의 `approve`는 `msg.sender`, 곧 트랜잭션을 보낸 사람이 허락을 거는 함수입니다. 그래서 컨트랙트를 거쳐 토큰을 쓰려면 사용자가 먼저 트랜잭션을 한 번 보내야 하고, 토큰만 있고 ETH가 없는 사용자는 시작도 못 합니다. 이 불편을 풀려는 시도는 여러 번 있었지만, EIP 문서가 짚듯 EIP-777처럼 기능을 크게 얹은 방식은 주류 컨트랙트에서 예상 밖의 동작을 만들었습니다.

ERC-2612는 범위를 좁게 잡았습니다. 다루는 문제는 `approve`가 `msg.sender`에 묶여 있다는 점 하나이고, 그 부분만 서명으로 대체합니다. `transfer`의 서명 버전 같은 건 일부러 넣지 않았습니다. 용도마다 수수료 구조가 다르고, `permit`과 보조 컨트랙트를 조합하면 만들 수 있기 때문입니다.

## permit이 하는 일

ERC-20에 세 함수가 더해집니다.

```solidity
function permit(address owner, address spender, uint value, uint deadline, uint8 v, bytes32 r, bytes32 s) external
function nonces(address owner) external view returns (uint)
function DOMAIN_SEPARATOR() external view returns (bytes32)
```

`permit`은 서명이 유효하면 `allowance[owner][spender]`를 `value`로 바꾸고, `nonces[owner]`를 1 올리고, `Approval` 이벤트를 냅니다. 조건은 네 가지입니다. 기한(`deadline`) 안일 것, `owner`가 0 주소가 아닐 것, 서명한 nonce가 현재 nonce와 같을 것, 서명이 `owner`의 것일 것입니다. 하나라도 어기면 되돌립니다.

서명하는 내용은 EIP-712 형식의 `Permit(owner, spender, value, nonce, deadline)`입니다. 누가 누구에게 얼마를 언제까지 허락하는지가 담겨 있고, nonce는 같은 서명을 두 번 쓰지 못하게 막습니다. 여기에 `DOMAIN_SEPARATOR`가 더해집니다. 토큰 이름, 버전, 체인 번호, 컨트랙트 주소를 묶은 값이라서 같은 서명을 다른 체인이나 다른 토큰에 가져다 쓸 수 없습니다. 지갑은 이 구조를 읽어서 이 사이트가 USDC 얼마를 쓰도록 허용한다는 식으로 사람이 읽을 수 있게 보여 줄 수 있습니다.

흐름은 세 단계입니다.

1. 사용자가 지갑에서 `Permit` 메시지에 서명합니다. 트랜잭션이 아니라서 가스비가 들지 않습니다.
2. 앱이 서명을 받아 컨트랙트 호출에 같이 실어 보냅니다.
3. 컨트랙트가 `permit`을 부르고 이어서 `transferFrom`으로 토큰을 가져갑니다. 이 모두가 트랜잭션 한 번 안에서 일어납니다.

트랜잭션을 보내는 사람이 사용자가 아니어도 되기 때문에, 앱이나 릴레이어가 가스를 대신 내 주는 설계도 가능합니다.

## USDC로 확인해 봤습니다

USDC(`0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48`)에 `eth_call`을 보내 봤습니다.

| 호출 | 응답 |
|---|---|
| `name()` | `USD Coin` |
| `version()` | `2` |
| `PERMIT_TYPEHASH()` | `0x6e71edae12b1b97f4d1f60370fef10105fa2faae0126114a169c64845d6126c9` |
| `DOMAIN_SEPARATOR()` | `0x06c37168a7db5138defc7866392bb87a741f9b3d104deb5094588ce041cae335` |

응답을 믿기만 하지 않고 해시를 직접 계산해 맞춰 봤습니다. 문서의 `Permit(address owner,address spender,uint256 value,uint256 nonce,uint256 deadline)` 문자열을 keccak256으로 해시하면 `PERMIT_TYPEHASH`와 정확히 같았습니다. 이름 `USD Coin`, 버전 `2`, 체인 번호 1, USDC 주소를 묶어 계산한 `DOMAIN_SEPARATOR`도 온체인 값과 일치했습니다.

그다음 서명이 실제로 통하는지 시험했습니다. 잔액이 없는 임시 키를 새로 만들어 같은 도메인과 타입으로 서명한 뒤, USDC의 `permit`을 `eth_call`로 호출했습니다. `eth_call`은 노드에서 시뮬레이션만 하고 블록에 기록하지 않아서 온체인에는 아무것도 남지 않습니다.

| 호출 | 결과 |
|---|---|
| 올바른 서명 (v=28) | 성공 |
| 같은 서명을 v=27로 호출 | `EIP2612: invalid signature`로 거부 |
| value를 1만 바꾼 서명 | `EIP2612: invalid signature`로 거부 |
| deadline을 과거로 바꾼 호출 | `FiatTokenV2: permit is expired`로 거부 |

v는 서명에서 서명자를 복구할 때 쓰는 값이라 27과 28 중 하나만 맞습니다. 값이 한 글자만 어긋나도 거부되는 것이 보입니다. 이 시험은 ethers 코드를 실행한 것이 아니라 같은 구조를 직접 구현한 서명으로 한 것이어서, 확인된 것은 이 서명 데이터의 구조를 USDC가 받아 준다는 점입니다.

DAI(`0x6B175474E89094C44Da98b954EedeAC495271d0F`)는 방식이 다릅니다. 같은 이름의 `permit`이 있지만 `PERMIT_TYPEHASH`가 `0xea2aa0a1be11a07ed86d755c93467f4f82362b452371d1ba94d1715123511acb`로 다릅니다. DAI 컨트랙트는 2019년 11월 13일에 배포됐고 ERC-2612는 2020년 4월 13일에 작성됐으니(문서 머리말 기준), DAI의 `permit`이 먼저 나온 방식입니다. 서명 구조가 `holder`, `spender`, `nonce`, `expiry`, `allowed`이고 금액 대신 허용 여부를 true와 false로 다룹니다. 이 구조의 해시도 위의 DAI typehash와 같았고, 이름 `Dai Stablecoin`과 버전 `1`로 계산한 `DOMAIN_SEPARATOR`도 온체인 값과 같았습니다. `permit`이 있다고 해서 같은 코드로 서명을 만들 수는 없다는 뜻입니다.

`permit`이 없는 토큰을 위한 해법도 메인넷에 있습니다. Permit2(`0x000000000022D473030F116dDEE9F6B43aC78BA3`)는 서명으로 토큰 이동을 처리하는 별도의 컨트랙트입니다. 흔히 Uniswap이 만든 것으로 알려져 있지만 소스에서 제작 주체를 직접 확인하지는 못했습니다. 검증된 소스의 주석은 서명 기반 전송은 SignatureTransfer에서, 허용량 기반 전송은 AllowanceTransfer에서 처리한다고 설명합니다.

## 코드로 보기

서명을 만드는 쪽은 ethers v6로 이렇게 씁니다. 이 코드는 실행해 보지 않았습니다.

```js
import { ethers } from "ethers";

const domain = {
  name: "USD Coin",
  version: "2",
  chainId: 1,
  verifyingContract: "0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48",
};
const types = {
  Permit: [
    { name: "owner", type: "address" },
    { name: "spender", type: "address" },
    { name: "value", type: "uint256" },
    { name: "nonce", type: "uint256" },
    { name: "deadline", type: "uint256" },
  ],
};
const owner = await signer.getAddress();
const message = {
  owner,
  spender,                         // 토큰을 쓸 컨트랙트
  value: 1_000_000n,               // USDC는 소수점 6자리, 1 USDC
  nonce: await usdc.nonces(owner), // 컨트랙트에서 읽은 현재 nonce
  deadline: Math.floor(Date.now() / 1000) + 600,
};
const sig = ethers.Signature.from(await signer.signTypedData(domain, types, message));
// sig.v, sig.r, sig.s를 permit 호출에 넘깁니다.
```

받는 컨트랙트는 `permit`과 `transferFrom`을 이어서 부릅니다. 아래 코드는 solc 0.8.26과 OpenZeppelin Contracts 5.6.1로 컴파일되는 것까지 확인했습니다.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";
import {IERC20Permit} from "@openzeppelin/contracts/token/ERC20/extensions/IERC20Permit.sol";
import {SafeERC20} from "@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol";

contract PermitVault {
    function depositWithPermit(
        address token, uint256 amount, uint256 deadline,
        uint8 v, bytes32 r, bytes32 s
    ) external {
        // permit이 이미 실행됐을 수 있으니 실패를 허용하고 allowance로 다시 확인
        try IERC20Permit(token).permit(msg.sender, address(this), amount, deadline, v, r, s) {} catch {}
        require(IERC20(token).allowance(msg.sender, address(this)) >= amount, "no allowance");
        SafeERC20.safeTransferFrom(IERC20(token), msg.sender, address(this), amount);
    }
}
```

## 조심할 점

1. 서명 선점입니다. 서명은 트랜잭션에 담겨 멤풀에 올라가는 순간 공개됩니다. 누군가 같은 서명으로 `permit`만 먼저 실행하면 nonce가 소진되어 내 원래 트랜잭션이 되돌려집니다. 공격자가 얻는 이익은 없지만 호출을 방해할 수 있어서, 위 코드처럼 `permit` 실패를 허용하고 `allowance`를 다시 확인하는 것이 통상적인 대응입니다.
2. 피싱입니다. `permit` 서명은 트랜잭션이 아니라서 가스 추정이나 전송 확인 화면이 뜨지 않습니다. 서명 한 번이 곧 토큰 사용 권한이니, 서명창에서 `spender`, `value`, `deadline`을 읽는 습관이 중요합니다. 금액이 무제한인 서명은 특히 조심해야 합니다.
3. 스마트 컨트랙트 지갑입니다. ERC-2612는 `ecrecover`로 EOA의 서명을 검증하기 때문에, 서명 검증을 컨트랙트가 직접 하는 지갑(ERC-1271 방식)은 이 서명을 만들 수 없습니다. 다음 글에서 다룰 [ERC-4337](/posts/erc-4337-account-abstraction/) 중 컨트랙트로 배포한 계정이 여기에 해당합니다. EOA에 코드를 위임한 7702 계정은 개인키가 그대로 있어서 EOA 서명을 만들 수 있습니다.
4. 도메인입니다. `DOMAIN_SEPARATOR`에 들어 있는 체인 번호가 바뀌었는데 예전 값을 계속 쓰는 구현이면 다른 체인의 서명을 받아들일 수 있습니다. 체인 번호가 바뀌면 다시 계산하는 구현인지 보는 것이 안전합니다.

## 확인하지 못한 것

- 위 컨트랙트를 배포하거나 실제 토큰으로 호출해 보지는 못했습니다.
- ethers 코드는 라이브러리를 설치하지 않아서 실행하지 못했습니다. 위의 USDC 시험은 같은 구조를 직접 구현한 서명으로 했습니다.
- Permit2는 소스의 주석과 함수 목록만 읽었고, 내부 로직을 끝까지 따라가거나 실제 전송을 해 보지는 못했습니다. 토큰마다 Permit2에 먼저 한 번 `approve`를 해야 한다는 점도 실행으로 확인하지 못했습니다.

## 정리

ERC-2612는 ERC-20에서 `approve`가 `msg.sender`에 묶여 있다는 점 하나만 서명으로 풀었습니다. USDC에서 해시를 직접 계산하고 서명을 시뮬레이션해 구조가 맞는 것을 확인했고, DAI는 같은 이름이어도 구조가 다르다는 것도 봤습니다. 서명 한 번이 곧 권한이니, 만드는 쪽은 선점 대응을, 쓰는 쪽은 서명 내용 확인을 챙겨야 합니다.
